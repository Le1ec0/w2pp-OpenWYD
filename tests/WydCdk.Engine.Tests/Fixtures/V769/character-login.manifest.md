- Contract decision: use the client-declared 1728-byte frame. The common DBSrv header declares the same fields and size; the client handler copies `MOB` and reads following fields at those offsets. The private 7.69 TMSrv header instead declares a 2640-byte message with an 816-byte/16-equipment MOB, and `DataServerPackageHandler` sends that full struct despite also declaring an 1832-byte client form. That source inconsistency is not a client-wire oracle.
- Source caveat: the 7.69 DBSrv handler comments out the Ext1/Ext2 data copies and does not zero-initialize the outgoing local struct. The client reads `Ext1.Data[0]` as Fake EXP; W2PP `extra.Hold` and the 7.69 TMSrv `Extra.Hold` -> `FakeExp` sender path establish that one semantic mapping. `W2ppCharacterLoginExtensionsV1Adapter` maps only that uint (rejecting signed-int overflow), and `CharacterLoginExtensionsV769` zeroes the remaining EXT1/EXT2 bytes. EXT1 Affect is not copied because the field order/width differs; status effects need the separate target `MSG_UpdateAffect` contract. This golden still proves layout only, not a complete login projection.
- Adapter status: `CharacterMobV769` and `W2ppCharacterMobV1Adapter` project the measured 1040-byte client MOB against [the compiled Win32 MOB golden](character-mob.manifest.md). `W2ppCharacterLoginV1Adapter` composes that projection with the 16-byte short-skill block, resolved spawn, explicit slot/client/weather fields, and mapped Fake EXP into the 1728-byte client DTO; the deterministic test validates the complete encoded frame. W2PP's single `LearnedSkill` word maps to target word 0; target word 1 (skills 200-246) is zero because the W2PP source MOB has no equivalent, and `MOBEXTRA.SecLearnedSkill` is a distinct field. This composer does not reproduce TMSrv's login-time derived-state mutations. Listener integration, runtime capture, separate Affect, EXT2 crosswalk, and client E2E remain pending.
